# 3. Software Development and Implementation

During my internship, I worked on the development of a desktop software application designed to demonstrate real-time data communication and a configurable multi-tenant software architecture. The main focus of my work was to understand how different software components could be combined into a maintainable application while allowing the same software to support multiple customers with different requirements.

## 3.1. Project Architecture and Development Environment

The project was developed using **Kotlin** on the JVM, with **JDK 21** as the target platform. I used **Gradle with Kotlin DSL** for build automation and dependency management. One of the important aspects of the project was learning how a build system can be used not only to compile an application, but also to control which customer-specific source files are included in a particular build.

The application was structured into separate packages according to their responsibilities. These included the WebSocket communication layer, data models, customer configuration, dependency injection, and the JavaFX dashboard. This separation made the application easier to understand and allowed individual components to be developed and modified without unnecessarily affecting the rest of the system.

## 3.2. Real-Time Data Communication with WebSocket

One of the main tasks in the project was implementing a real-time communication layer using the **WebSocket API**. The application establishes an asynchronous WebSocket connection to an external data source and continuously receives data through this connection.

I worked with the `java.net.http.WebSocket` API provided by JDK 21. The incoming messages were received through callback methods such as `onOpen`, `onText`, `onError`, and `onClose`. Since a WebSocket message can be delivered in multiple fragments, the received text fragments were accumulated using a `StringBuilder` and processed when the final fragment was received.

The received data was represented using Kotlin data classes and processed using the **Jackson** library. This allowed the application to convert incoming JSON messages into structured objects that could be used by the rest of the application.

Another important aspect was the asynchronous nature of the communication. Data was received on background threads, while JavaFX requires its user interface components to be modified from the JavaFX Application Thread. Therefore, UI updates were transferred to the appropriate thread using `Platform.runLater`. This allowed the application to process continuous incoming data without violating JavaFX's thread-safety requirements.

## 3.3. Multi-Tenant Architecture

The most important architectural feature of the project was its **multi-tenant structure**. The purpose of this design was to allow a single software codebase to support multiple customers while giving each customer a different set of available screens and features.

Each customer has a configuration containing information such as the customer name and available dashboard screens. The supported screens are represented using a common feature structure, while each customer can enable a different subset of these features.

For example, one customer may only have access to the basic monitoring screen, while another customer may also have additional performance or portfolio-related screens. The dashboard is therefore not fixed; it is dynamically constructed according to the selected customer's configuration.

This architecture helped me understand an important software engineering problem: how to avoid maintaining separate versions of the same application for different customers. Instead of duplicating the entire project, common functionality is kept in the main codebase and customer-specific differences are represented through configuration and feature definitions.

## 3.4. Customer Management and User Interaction

Another significant part of the project was the development of a **Customer Creator** application. The purpose of this tool was to allow an administrator to create new customer profiles through a graphical user interface rather than manually creating and configuring source files.

Through the interface, an administrator can enter a customer name and select the screens that should be available to that customer. The selected features are validated according to predefined rules before the customer is created. This prevents incompatible or incomplete feature configurations from being generated.

After the administrator confirms the configuration, the system automatically generates the required Kotlin source files for the new customer. The generated files contain the customer's configuration and feature definitions and are placed in the appropriate customer-specific source directory.

This approach significantly simplifies the process of adding customers. Instead of requiring a developer to manually create multiple files and ensure that package names, class names, and configurations are consistent, the administrator can perform the operation through a dedicated interface.

## 3.5. Dependency Injection with Koin

I also worked with **Koin** to implement dependency injection in the application. Customer-specific configuration objects and other shared components are registered in the Koin container and retrieved by the parts of the application that require them.

Using dependency injection reduced direct dependencies between classes. For example, the dashboard does not need to know how a particular customer's configuration object is created. It simply requests the required dependency from the container.

Working with Koin helped me understand the practical benefits of dependency injection, particularly in terms of modularity, maintainability, and testability. It also demonstrated how a dependency injection framework can be integrated into a Kotlin application without requiring a large amount of configuration.

## 3.6. Gradle-Based Customer Configuration

Gradle was also an important part of the multi-tenant architecture. The build process was configured so that a specific customer could be selected when building or running the application.

The customer selection is passed as a Gradle property, and the build process includes the corresponding customer-specific source files and resources. This means that the resulting application can be packaged specifically for a particular customer instead of containing all customer configurations.

This design combines **build-time configuration** with the application's runtime customer configuration. As a result, the same main codebase can be used to produce different customer-specific versions of the application while keeping the common functionality shared.

## 3.7. Feature Validation and Application Reliability

Since different customers can have different combinations of screens, certain combinations need to be controlled. For this purpose, I worked with a rule-based validation structure consisting of `FeatureRules` and `FeatureValidator`.

The rules define which features require other features and which features are incompatible with each other. Before the application starts, the selected customer's feature configuration is validated. If an invalid configuration is detected, the application stops with an appropriate error instead of starting with an inconsistent setup.

This approach follows the **fail-fast** principle. Detecting configuration errors at startup makes potential problems easier to identify and prevents invalid customer configurations from reaching later stages of execution.

## 3.8. Overall Contribution and Learning Outcome

The main value of this project was that it brought together several software engineering concepts within a single application. Rather than developing an isolated user interface or a simple data receiver, I worked on a system involving real-time communication, asynchronous processing, dependency injection, build automation, configurable features, and multi-tenant customer management.

Through this work, I gained practical experience with **Kotlin, JavaFX, WebSocket communication, Gradle, Koin, JSON processing, and software architecture**. More importantly, I learned how design decisions such as dependency injection, feature configuration, build-time customization, and automated customer creation can be used to make a software product easier to maintain and adapt to different customer requirements.
